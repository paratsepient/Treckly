# Прототип: щоденні замовлення за Попереднім переліком

Робочий макет системи обліку майна та погодження заявок. Синтетичні дані, запуск на локальному ПК без інтернету.
Окремий продукт, не модуль IndeX. UI Kit скопійований з основної гілки IndeX.

## Стек
pnpm workspaces (pnpm 11.23.0) · esbuild + React 19.3.1 + TypeScript 5.9.3 strict · TanStack Router + Query ·
Zod (контракт) · Hono у браузері як мок-бекенд · PGlite + Drizzle (запасний варіант — Dexie) · React Hook Form ·
faker з фіксованим seed · тести `node:test` (jsdom + axe-core) · Playwright (e2e, ще не додано).
Версії React/TS, збирач, лінтер — як в IndeX (див. `UPSTREAM.md`). Якщо IndeX відрізняється — перемагає IndeX.

> **Змінено 2026-11-11 за стеком IndeX (origin/main 0450585):**
> - Vite → **esbuild** (скрипт `apps/web/scripts/serve.ts`); у IndeX Vite немає.
> - Vitest + Testing Library → **`node:test`** + jsdom + axe-core (як в IndeX).
> - Лінтера і форматера в IndeX **немає** — тут теж не додано (перевірка якості: `tsc` strict).
> - Стилі: звичайний CSS на токенах `--ix-*`, теми через `data-theme="light|dark"` (не CSS Modules).
> - Пакети збираються `tsc` у `dist` і підключаються через `exports`; Nx не використовуємо, збірка — `pnpm -r`.
> - Ще не встановлено (немає в IndeX, додаємо за згодою): TanStack Router/Query, Zod, Hono, PGlite, Drizzle,
>   React Hook Form, faker, Playwright. Імена внутрішніх пакетів: `@dsp/domain|contract|api|db|seed|web`.

## Правила коду
- Екрани звертаються лише до клієнта API, ніколи до бази.
- Домен не знає про базу і реальний час: дата — з `Clock` (від нього залежить «Наступний день»).
- Копію UI Kit не змінюємо. Нові компоненти (трек 5 рівнів) — у `apps/web` на токенах набору.
- Жодних колірних літералів у CSS — лише токени. Теми Light і Dark.
- Стани даних — через `DataState`, не через нулі чи порожні таблиці.
- Кожна зміна стану: транзакція + запис у журнал (append-only) + ключ ідемпотентності + версія.
- Жодних зовнішніх URL у збірці: шрифти й ресурси локально.
- Тексти інтерфейсу — українською.

## Ключові бізнес-правила
1. 5 рівнів: в/ч → бригада → РУ → Адміністрація по напрямку → Відділ оборонних ресурсів і Голова.
2. На рівні обирають заявки і кнопкою формують денний перелік; необрані лишаються в черзі.
   Непогоджений перелік можна розформувати. Погодження — з числовим номером СЕДО.
3. Відмова: заявка каскадом іде до автора з обов'язковою приміткою, усі нижчі рівні отримують сповіщення.
   Виправляє лише автор; нова версія йде з першого рівня. Часткового погодження немає.
4. Автоперевірки при створенні: позиція в Попередньому переліку 2027 (прив'язаний до напрямку),
   доступна кількість, КЕКВ, залишок бюджету.
5. Бюджет резервується лише при затвердженні Головою. Заміна в межах одного КЕКВ ліміт не витрачає, на інший — витрачає.
6. Відкликати заявку можна, поки її не затверджено на останньому рівні.
7. «Заміна погоджена» — лише після затвердження Головою разом із формуванням витягу по в/ч.
8. СЕДО не замінюємо: система лише дає трек і зберігає номери СЕДО.

## Команди
- `pnpm install` — встановити залежності
- `pnpm dev` — dev-сервер (http://localhost:4340/, `PORT` змінює порт)
- `pnpm build` — збірка всіх пакетів і `apps/web` (результат у `apps/web/public/dist`)
- `pnpm typecheck` / `pnpm check` — перевірка типів / повна перевірка пакетів
- `pnpm check` — типи й тести всіх пакетів (`node:test`); один пакет: `pnpm --filter @dsp/domain check`
- `pnpm --filter @dsp/db generate` — нова міграція Drizzle після зміни схеми, потім `pnpm --filter @dsp/db embed`
  (SQL вбудовується в `migrations.generated.ts`, бо в браузері немає файлів; `check:migrations` це контролює)
- `pnpm --filter @dsp/seed generate` — перегенерувати `seed-data.json` після зміни генератора (`check:data` перевіряє актуальність).
  Браузер бере готові дані з `@dsp/seed/browser`, **без `faker`**: його рядки зі сторонніми адресами не мають потрапляти в збірку.
- `pnpm --filter @dsp/web check:offline` — збірка без зовнішніх ресурсів (запускається і в `build`)
- «Скинути демо» — кнопка в демо-панелі (`resetDemo()`: чиста схема + той самий початковий стан); e2e, lint — пізніше (lint у IndeX відсутній)

## Відомі обмеження
- **Одна вкладка.** База PGlite в IndexedDB має одного власника; друга вкладка отримує повідомлення (Web Locks) замість зависання.
  Ролі перемикаються в демо-панелі однієї вкладки.
- **Прогалина домену:** дублікат id рядків у заявці не відхиляється доменом (на базі це 500). UI генерує унікальні id.
