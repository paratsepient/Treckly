# Прототип: щоденні замовлення за Попереднім переліком

Робочий макет системи обліку майна та погодження заявок. Синтетичні дані, запуск на локальному ПК без інтернету.
Окремий продукт, не модуль IndeX. UI Kit скопійований з основної гілки IndeX.

## Джерела правди (Notion)
- Концепція: «Система обліку майна та погодження рапортів — концепція», розділи 01–10
- План прототипу: 11 · План прототипу
- Документ розробки: 12 · Документ розробки прототипу — головний документ для коду
Якщо код і документ розходяться — питай, не вирішуй сам.

## Стек
pnpm workspaces (pnpm 11.23.0) · esbuild + React 19.3.1 + TypeScript 5.9.3 strict · TanStack Router + Query ·
Zod (контракт) · Hono у браузері як мок-бекенд · PGlite + Drizzle (запасний варіант — Dexie) · React Hook Form ·
faker з фіксованим seed · тести `node:test` (jsdom + axe-core) · Playwright на встановленому Chrome (e2e + axe у `e2e/`).
Версії React/TS, збирач, лінтер — як в IndeX (див. `UPSTREAM.md`). Якщо IndeX відрізняється — перемагає IndeX.

> **Змінено 2026-11-11 за стеком IndeX (origin/main 0450585):**
> - Vite → **esbuild** (скрипт `apps/web/scripts/serve.ts`); у IndeX Vite немає.
> - Vitest + Testing Library → **`node:test`** + jsdom + axe-core (як в IndeX).
> - Лінтера і форматера в IndeX **немає** — тут теж не додано (перевірка якості: `tsc` strict).
> - Стилі: звичайний CSS на токенах `--ix-*`, теми через `data-theme="light|dark"` (не CSS Modules).
> - Пакети збираються `tsc` у `dist` і підключаються через `exports`; Nx не використовуємо, збірка — `pnpm -r`.
> - Додано за згодою користувача: `docx` 9.15.0 (експорт у Word; вантажиться окремим чанком лише при експорті). Друк у PDF — через прихований iframe без бібліотек.
> - Playwright (`@playwright/test` 1.64.1) додано за згодою користувача: **без завантаження браузера**, тести йдуть на встановленому в системі Chrome
>   (`channel: "chrome"`). axe — той самий `axe-core`, що в IndeX, підключений у сторінку.
> - Решта бібліотек з документа (TanStack Router/Query, Zod, Hono, PGlite, Drizzle, React Hook Form, faker) встановлена за згодою.
>   Імена внутрішніх пакетів: `@dsp/domain|contract|api|db|seed|web|e2e`.

## Правила коду
- Екрани звертаються лише до клієнта API, ніколи до бази.
- Домен не знає про базу і реальний час: дата — з `Clock` (від нього залежить «Наступний день»).
- UI Kit дає токени й базові елементи (кнопки, поля, таблиці, діалоги, діаграми). Оболонка застосунку власна (`apps/web/src/app`: навігація з підписами,
  сітка сторінки, бічна картка окремою колонкою) — `AppShell`/`WorkspaceLayout` набору не використовуємо. Зміни в копії набору дозволені
  користувачем, але мінімальні й кожна записана в `UPSTREAM.md` («Локальні зміни»). Нові компоненти — у `apps/web` на токенах набору.
- Розкладка: 1024 px — навігація закріплена (нижче — висувна панель); 1280 px — бічна картка колонкою (нижче — висувна або блок під вмістом);
  до 720 px таблиці показують лише головні стовпці. Стилі: `shell.css` (оболонка), `content.css` (сітки, адаптивність), `app.css` (компоненти).
- Жодних колірних літералів у CSS — лише токени. Теми Light і Dark.
- Стани даних — через `DataState`, не через нулі чи порожні таблиці.
- Кожна зміна стану: транзакція + запис у журнал (append-only) + ключ ідемпотентності + версія.
- Жодних зовнішніх URL у збірці: шрифти й ресурси локально.
- Тексти інтерфейсу — українською.

## Ключові бізнес-правила
1. 5 рівнів: в/ч → бригада → РУ → Адміністрація по напрямку → Відділ оборонних ресурсів і Голова.
2. На рівні обирають заявки і кнопкою формують денний перелік; необрані лишаються в черзі.
   Непогоджений перелік можна розформувати. Погодження — з числовим номером СЕДО.
   Автор реєструє рапорт у СЕДО сам і вводить реєстраційний номер при поданні (`Request.sedoNumber`; нова версія — новий номер).
   **Рівень 5:** Відділ оборонних ресурсів формує остаточний перелік, друкує або завантажує його, несе на підпис Голові
   й відмічає «Підписано Головою» з номером СЕДО (`signerKind(5) = "preparer"`). Голова в системі не погоджує —
   лише моніторинг: реєстр і зведення, запланований і остаточний перелік (рішення користувача 2026-11-12).
   Якщо Голова не підписав — Відділ відмічає «Голова не підписав» з обов'язковою приміткою (`markNotSigned`): усі заявки
   переліку повертаються авторам (як відмова, рівні 4–1 отримують сповіщення), перелік розформовується, бюджет не змінюється.
   У «Звірці з переліком» на рівні 5 — залишки ініціатора («На базі», «Отримано») того, що просять (для заміни — нового предмета).
3. Відмова: заявка каскадом іде до автора з обов'язковою приміткою, усі нижчі рівні отримують сповіщення.
   Виправляє лише автор; нова версія йде з першого рівня. Часткового погодження немає.
4. Автоперевірки при створенні: позиція в Попередньому переліку 2027 (прив'язаний до напрямку),
   доступна кількість, КЕКВ, залишок бюджету. **Автор подає лише те, що заплановано на його в/ч** («Моє майно → Заплановано»):
   позиції немає в плані в/ч — `NOT_IN_LIST`, кількість більша за план — `QTY_EXCEEDED` (рішення користувача 2026-11-12).
   У виборі редактора лише позиції плану в/ч; діє менша з меж: план в/ч і доступне за переліком напрямку.
   План в/ч рахується **разом з іншими заявками в/ч** (усі, крім чернеток, відкликаних і невиконаних): `QTY_EXCEEDED` з
   `alreadyOrdered`. Позиція в іншій незавершеній заявці в/ч (на рівні, у переліку, повернута) — `POSITION_BUSY`, з вибору зникає;
   якщо закупівля позиції за іншою заявкою вже почалась — попередження `POSITION_BUSY/PURCHASE_STARTED`, подати можна.
5. Бюджет резервується лише при затвердженні Головою. Заміна в межах одного КЕКВ ліміт не витрачає, на інший — витрачає
   суму нового предмета з нового КЕКВ; старий КЕКВ **не вивільняється** (рішення користувача: вивільняти нічого, резерву не було).
6. Відкликати заявку можна, поки її не затверджено на останньому рівні.
7. «Заміна погоджена» — лише після затвердження Головою разом із формуванням витягу по в/ч.
8. СЕДО не замінюємо: система лише дає трек і зберігає номери СЕДО.
9. Запланований перелік закупівель (екран `#/planned`, `GET /api/planned-list`) бачать уповноважені й керівники всіх рівнів — у своїй зоні:
   в/ч — свою в/ч, бригада — свої в/ч, РУ — свої в/ч (план = сума планів в/ч); напрямок, Відділ і Голова — увесь перелік напрямку
   (рішення користувача 2026-11-12). Автор і адміністратор — 403.
   Сума планів в/ч за позицією не може перевищувати план напрямку (`allocationIssues`; `applySeed` відхиляє такий план,
   екран показує «Розподілено більше, ніж за напрямком»).
12. ТВО (адміністратор, екран `#/acting`): призначає заступника замість уповноваженої особи чи керівника рівня.
   Поки призначення чинне, заступник діє з роллю того, кого заміщає (посада «ТВО: …»), журнал пише `data.actingFor`
   («Ім'я (ТВО за Ім'я)»). Одна особа — одне чинне призначення в кожен бік; знято — повертається своя роль (рішення 2026-11-12).
11. Закупівля й видача (Відділ оборонних ресурсів — уповноважена особа рівня 5, екран `#/procurement`; рішення користувача 2026-11-12): після витягу заявка «чекає закупівлі». Підтвердження закупівлі —
   документ приймання, отримувач, фактична кількість (має збігатися, інакше `QTY_MISMATCH`): заявка «Виконано · на складі бази»,
   рядки «Закуплено» / «Замінено», нове — в «На базі» в/ч. Видача одним актом: нове — в «Отримано», старе із замін — на інший облік
   («Виконано · видано»). «Не виконано» з приміткою: статус заміни знімається, резерв бюджету вивільняється (рішення 2026-11-12).
10. Рапорт: автор уводить лише позиції й обґрунтування, решту (адресат, текст прохання, таблиці, підсумок за КЕКВ, підпис)
   дає шаблон `apps/web/src/lib/raport.ts`; перегляд, друк і Word — з однієї моделі. Без обґрунтування заявку не подати.
   Форму шаблону користувач підтвердив 2026-11-11 — змінювати лише за його зразком.
   2026-11-12 за згодою користувача: у заявці й рапорті — служба (відділ, обов'язкова; «для потреб в/ч … (служба …)»),
   джерело фінансування (загальний / спеціальний фонд, «за рахунок … фонду») і стан майна, яке замінюють
   (непридатне / потребує ремонту / втрачене; стовпець «Стан замінюваного», обов'язковий для заміни).
   2026-11-12 за проханням користувача розділи підписано явно: «Заміна: замість запланованої позиції — інший предмет»
   (стовпці «Замість» / «Просимо натомість», зміна КЕКВ як «2210 → 3110») і «Закупівля за переліком (без заміни)».

## Команди
- `pnpm install` — встановити залежності
- `pnpm dev` — dev-сервер (http://localhost:4340/, `PORT` змінює порт)
- `pnpm build` — збірка всіх пакетів і `apps/web` (результат у `apps/web/public/dist`; папка очищається перед збіркою)
- `pnpm start` — готова збірка на http://localhost:4340/ (статичний сервер без залежностей); для показу, не для розробки
- `pnpm test:e2e` — сценарії E1–E7 і axe у Chrome (потрібна `pnpm build`; сервер береться з уже запущеного `pnpm start` або `pnpm dev`)
- `pnpm typecheck` / `pnpm check` — перевірка типів / повна перевірка пакетів
- `pnpm check` — типи й тести всіх пакетів (`node:test`); один пакет: `pnpm --filter @dsp/domain check`
- `pnpm --filter @dsp/db generate` — нова міграція Drizzle після зміни схеми, потім `pnpm --filter @dsp/db embed`
  (SQL вбудовується в `migrations.generated.ts`, бо в браузері немає файлів; `check:migrations` це контролює)
- `pnpm --filter @dsp/seed generate` — перегенерувати `seed-data.json` після зміни генератора (`check:data` перевіряє актуальність).
  Браузер бере готові дані з `@dsp/seed/browser`, **без `faker`**: його рядки зі сторонніми адресами не мають потрапляти в збірку.
- `pnpm --filter @dsp/web check:offline` — збірка без зовнішніх ресурсів (запускається і в `build`)
- «Скинути демо» — кнопка на екрані «Демо-середовище»: чиста схема **без жодного рапорту** (переліків, витягів, сповіщень, журналу);
  структура, ролі, Попередній перелік, план в/ч і ліміти лишаються, затверджено — нуль (рішення користувача 2026-11-12).
  «Заповнити прикладами» — та сама чиста схема з демо-прикладами (`resetDemo(..., { withExamples: true })`, `POST /api/demo/reset {withExamples}`).
  Перший запуск у новому браузері — з прикладами.

## Відомі обмеження
- **Одна вкладка.** База PGlite в IndexedDB має одного власника; друга вкладка отримує повідомлення (Web Locks) замість зависання.
  Ролі перемикаються на екрані «Демо-середовище» (кнопка «Демо» вгорі; ролі розставлено за ієрархією) в одній вкладці.

## Готово, якщо
Сценарії E1–E7 з документа розробки проходять, усі переходи процесу покриті тестами,
`UPSTREAM.md` містить коміт IndeX, прототип запускається на ПК без інтернету.
